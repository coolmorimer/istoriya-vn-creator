# Публикация Истории

Исходники публикуются в Git, готовые файлы — в GitHub Releases. Версия, тег и манифест должны указывать на один выпуск; уже опубликованные файлы нельзя молча заменять.

## Структура

- `src/`, `src-tauri/`, `runtime/` — редактор и движок сборки.
- `public/`, `examples/` — переиспользуемые ресурсы и исходники примеров.
- `tests/`, `scripts/` — проверки, сборка и подготовка поставки.
- `installer/` — Inno Setup.
- `docs/INSTALL.md`, `docs/DEVELOPMENT.md`, `docs/manual034/` — пользовательская и техническая документация.
- `docs/releases/<version>.md` — короткое описание публичного выпуска.
- `docs/RELEASE_<version>.md` — подробный отчёт с границами проверки.

В Git не входят SDK, зависимости, сборочные кэши, установщики, игровые ZIP, PDF/HTML, пользовательские проекты, ключи, `.env`, raw QA-профили и `design-qa.md`. Большие переносимые примеры публикуются отдельными Release assets. Скриншоты инструкции и происхождение готовой графики сохраняются с исходниками.

## Подготовка

1. Согласуйте версии `package.json`, lock-файлов, Cargo и Tauri. Запустите проверки из [DEVELOPMENT.md](DEVELOPMENT.md), включая фактический EXE и произведённые им игры.
2. Соберите установщик через `scripts/build-native-installer.ps1`. `-SkipBuild` допустим только для неизменённого проверенного EXE. Скрипт сверяет соседний runtime, проверяет подпись bootstrapper Microsoft и выдаёт `packaging-manifest.json`.
3. Обновите README, установку, changelog и описание выпуска. Не называйте незавершённый перенос или локальные проверки полной production-приёмкой.
4. Выполните `node scripts/check-public-source.mjs` и `git diff --check`. Просмотрите diff, добавьте только предназначенные для публикации файлы и сделайте коммит.

## Подготовка файлов версии 0.2.35

Используйте отдельную папку на диске с достаточным свободным местом. Пример локальных путей:

```powershell
node scripts/prepare-public-release.mjs --directory D:/Istoriya-Releases/0.2.35 --verification D:/IstoriyaQA/engine-035/engine-verification-manifest.json --previous D:/Istoriya-Releases/0.2.34/public
```

Команда сверяет версию, SHA EXE, исходники конвейера и все runtime-модули с проверкой; копирует только разрешённые файлы. Руководство и примеры сверяются с SHA предыдущей поставки, переносимые проекты проверяются на структуру и локальные пути. Готовая папка `public/` содержит только публичные файлы, сокращённый манифест без raw QA-путей и `SHA256SUMS.txt`. При другом содержимом существующего файла команда отказывает, а не перезаписывает его. Исходное дерево должно быть чистым и закоммиченным.

## Git и GitHub Release

Проверьте, что удалённая ветка не содержит чужих новых коммитов. Отправляйте ветку и тег без `--force`; обновление `main` допускается только fast-forward. Аннотированный тег `v0.2.35` должен указывать на коммит, записанный в `release-manifest.json`.

Создайте draft Release с флагом prerelease и описанием `docs/releases/0.2.35.md`. Загрузите только файлы из подготовленной `public/`, без raw манифестов QA и локальных профилей. Сверьте размер и GitHub SHA-256 каждого asset с локальным файлом. Только затем снимите draft. Не включайте production-статус и не засчитывайте неуспешный CI как приёмку.

После публикации проверьте доступность release, коммит ветки и тега, число файлов и суммы. При неопределённом результате сетевой операции сначала прочитайте состояние GitHub; не повторяйте создание или замену вслепую. Старые теги и Release assets остаются неизменными.
